# Testudines icon: mandatory apply-and-verify workflow

## The mistake this skill exists to prevent

A real incident on this app's earlier icon: several rounds of tweaks (moon
size and position) were done by rendering a PNG into a scratch directory,
showing the developer a preview, and waiting for confirmation before touching
the real icon. Several rounds of "does this look right?" passed, and the
actual app icon was never regenerated or rebuilt. The developer had no way to
tell from the running app or the committed files that anything had changed,
because nothing had. That was a process failure, not a rendering detail.

**The core error: treating "show a preview and ask if it looks right" as a
stopping point for icon work.** A preview is a mid-task checkpoint, never the
deliverable.

## The rule

**Every icon change reaches the actual app in the same turn it is made, with
no "let me know if this looks right first" pause.** Every icon edit does all
of these steps, every time:

1. Edit `scripts/make_icon.py` (the icon is drawn in code with Qt; there is
   no external artwork) and run it from the repo root:
   `uv run python scripts/make_icon.py`. It writes the 1024px
   `src/testudines/assets/icon.png`, which is both the window icon and the
   source of every packaged icon.
2. Rebuild the app: `scripts/build_macos.sh`. It turns `icon.png` into the
   `.icns`, self-tests and signs the app, and refreshes Launch Services so
   Finder and the Dock don't show a cached icon.
3. Launch `dist/Testudines.app` and look at the icon in the Dock and the
   window.
4. Only then report the change as done, as something that already happened
   ("rebuilt and verified"), not something pending approval.

Windows builds (`scripts/build_windows.ps1` and the GitHub Actions workflow)
use the same `icon.png`, so no separate Windows step is needed.

If you show the developer a rendered preview at all, it must be the *same*
`icon.png` already baked into the rebuilt app, never a separate scratch-only
render. Never show a preview and wait: act first, then report.

## Why this isn't wasted work if the developer wants another revision

Regenerating and rebuilding is scriptable. The cost of *not* doing it (the
developer looking at a stale app, concluding nothing happened, or losing
track of which round is live) is much higher than one extra build per
revision. Apply and rebuild every time, however small the tweak.

## Cleanup

Scratch scripts and PNGs belong in the session scratchpad directory, not the
repo. Delete them once `icon.png` has been regenerated by `make_icon.py`.

## Design rules (learned from real mistakes on this app's icons)

**1. If the developer supplies a reference image for the icon, composite
that exact file. Never redraw, retrace or "reinterpret" it.** Load it with
`QImage(path)`; the only transform allowed is a uniform resize (same aspect
ratio) to fit the composition. Don't recolor it, redraw its shapes or "clean
it up", even if a lookalike would be close. The developer asked for *that
image*.

**2. Never resize, rescale or reposition an established element without being
asked, including "shrinking it to make room" for something new.** This
happened once: adding a scenic background silently shrank the main artwork
to fit. Hold an established element's scale constant and make new elements
fit around it. If something can't fit without resizing it, stop and ask.

**3. Never add unrequested styling (outlines, shadows, glows, flourishes,
gradients, decorative extras), even if it would plausibly look better.** This
happened once: curl flourishes were added beside the app's name unasked and
had to be removed. The standing instruction: *"for this development please
only add what i ask to the best of your ability. there's no need to embellish
or improve."* If something would clearly help, suggest it in your reply;
don't add it.

**4. When a request changes one visual property (size, color, position),
change only that property, by a moderate step.** This happened once: asked to
make the moon "a bit larger", it was roughly doubled in one jump, prompting
"why did you make such a drastic increase in size instead of scaling it
gradually?" A single "bigger/smaller" request moves the value about 20-40%,
so the developer can steer with small corrections.

**5. Font and style choices must avoid cultural or thematic associations the
developer didn't ask for.** This happened once: a typeface was rejected
because its letterforms "implied some east-asian reference" that was never
requested. Check what associations a typeface or motif carries beyond the
literal property asked for (curvy, bold, serif).

**6. Measure, don't eyeball, when a request asks for precise placement.**
This happened once: text was guessed into a band of the artwork and reported
as "pushed to the top"; the true band, found by scanning the image's pixel
colors, was well off the guess. When a request implies exact alignment,
derive the coordinates from the artwork's actual geometry (the shapes in
`make_icon.py`, or the pixels of a supplied image), not a visual guess.
